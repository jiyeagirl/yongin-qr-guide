# 관리자 웹 (`/admin/`)

기준 문서는 **`admin/admin_specifications.md` (관리자 웹 기능명세서 v1.6)** 이다.
화면은 **열다섯이고 번호가 M01 ~ M15 로 이어진다.** 환경 설정 화면이 빠지면서
(2026-08-24) 한동안 빈 M15 를 남겨 두었는데, v1.5 에서 뒤 번호를 당겼다 —
**계정 관리가 M16 에서 M15 가 되었다.** 옛 문서의 「M16」은 지금의 M15 다.

> **범위가 좁다.** 명세서 머리말이 그것을 못 박았다 —
> "개별 건의 조회·수정·신규 등록과 오류신고 기반 보정. **데이터 일괄 적재, 매칭, 갱신,
> 검수는 개발 쪽에서 처리하며 별도 문서(데이터 매칭 및 검수 기획)로 분리한다.**"
>
> 그래서 이 화면들이 하는 일은 한 가지다: **한 건씩 고치고, 한 건씩 새로 넣는다.**
> 무엇이 빠졌고 왜 빠졌는지는 아래 「범위 밖으로 나간 것」에 있다.

## 시민용과 왜 완전히 나누는가

**시민용 앱에서 들어갈 수 있는 입구를 두지 않는다.** QR 을 찍고 들어온 시민이 관리자
화면을 볼 이유가 없고, 로그인이 붙는 순간 그 링크는 실패하는 문으로만 남는다. 그래서
주소도 폴더도 나눈다 — `/screens/main/` 과 `/admin/` 은 서로를 가리키지 않는다.
(검수 입구인 저장소 루트 `index.html` 에만 링크가 있다.)

**디자인 시스템 진입점도 나눈다.** `design-systems/index.js` 는 시민용, `admin.js` 는
관리자용이다. 관리자 컴포넌트를 `index.js` 에 합치면 재수출을 타고 시민용 모바일 번들에
데이터 표와 다이얼로그가 들어간다 — 길에서 QR 을 찍는 사람이 내려받을 이유가 없는 것들이다.
합치지 않은 결과, 관리자 화면을 열 개 만든 뒤에도 시민용 번들은 **95모듈 751KB 그대로**다.

## 화면

**대상을 부르는 이름은 「골목형 상점가」다** (2026-08-24) — 메뉴 · 제목 · 단추 · 다이얼로그 · 토스트 ·
항목명까지 줄이지 않고 그대로 적는다. 지정 제도의 이름이고 시민 화면도 그렇게 부른다.
예외 하나: 오류신고의 「대상 유형」 값(`상점가`)은 **시민 신고 폼과 함께 쓰는 저장값**이라
바꾸지 않았다 — 바꾸면 이미 접수된 건의 값과 갈린다.

그때의 번호가 M15 였고, 지금 그 번호는 계정 관리의 것이다).
두 구획이었고 둘 다 이 화면의 일이 아니었다.

- **서비스 운영 설정** (안내 범위 · 배너 기준 · 상점가 임계 거리 · 신규 매장 판정 기간 ·
  코스 반경 · 탭별 지도 확대 단계) → **개발 쪽.** 개별 건이 아니라 화면 전체가 도는
  방식을 정하는 값이다. 게다가 화면에 서 있는 내내 아무 데도 연결되지 않았다 —
  `config.js` 는 모듈 상수라 관리자가 밀어 넣을 수 없어서, 담당자가 반경을 고쳐도
  시민 화면은 그대로였다. 값 자체는 그 코드에 그대로 있다.
- **변경 이력** → 기록은 계속 쌓인다 (`data/store.js` 의 `readHistory`). 없어진 것은
  **보는 자리**이고, 다시 둔다면 대시보드 아래가 자연스럽다.

**목록과 등록·수정을 한 파일에 둔다.** 명세서는 M03/M04 처럼 둘로 나눠 세지만, 폼은
목록 위에 뜨는 다이얼로그다. 페이지를 나누면 335곳에서 조건을 좁혀놓고 한 곳 눌러본 뒤
돌아왔을 때 필터·쪽 번호·스크롤이 통째로 초기화된다 — 명세서 1장의 "상세 복귀 시
필터·스크롤 유지"를 지키는 가장 짧은 방법이 애초에 목록을 언마운트하지 않는 것이다.
(시민용 셸이 상세를 오버레이로 여는 것과 같은 판단이다.)

**공공시설 관리가 기준 화면이다.** 골격(머리 → 필터 줄 → 표 → 다이얼로그 폼 → 삭제 확인)을
거기서 정하고 나머지가 복제한다. 새 관리 화면을 만들 때 배치를 다시 정하지 않는다.
**목록을 좁히는 것은 전부 필터 줄의 고르개다** (2026-08-24) — 공공시설의 유형만 제목 아래
탭 줄이었는데, 탭이 나쁜 것이 아니라 **혼자 다른 것**이 값이라 다른 화면과 같은 자리
(검색창 왼쪽)로 내렸다.

## 범위 밖으로 나간 것 (2026-08-20 명세서 개정)

명세서가 관리자의 일을 **한 건 단위**로 좁히면서 다섯 가지가 빠졌다. 하나씩 이유가 다르고,
그 이유가 전부 같은 곳을 가리킨다 — **화면에서 결과를 되돌릴 수 없는 일은 화면의 일이 아니다.**

| 빠진 것 | 어디 있었나 | 왜 빠졌나 |
| --- | --- | --- |
| **매칭 검수 큐** | 화면 하나 (구 M07) | 실패를 손보는 일이 곧 매칭을 다시 돌리는 일이다 |
| **공공데이터 동기화** | 화면 하나 (구 M18) | 원본 조회·비교·반영 전부 서버 일이다 |
| **점포 일괄 업로드** | M05 의 다이얼로그 | 5,000행을 한 번에 넣고 화면에서 되돌릴 방법이 없다 |
| **구역 주소 목록 · 재매칭** | M04 의 1:N 편집기 | 주소를 손보는 일이 곧 매칭을 다시 돌리는 일이다 |
| **게시값 대비 산출값 비교** | 상점가 목록의 경고 | 명세서 2-1: "340 대 335처럼 차이를 알아도 **어느 5곳인지 모르면 고칠 수 없기 때문**" |

함께 사라진 작은 것들:

- **`sort_order` 노출 순서** (▲▼ 로 옮기던 것) — 항목표에서 빠졌다. 32곳의 차례는
  시민 화면이 거리로 정한다
- **공공시설 `source`** (원본 · 원본수정 · 직접등록) — 동기화가 어느 필드를 덮어쓸지
  정하는 값이었다. 읽는 곳이 없어졌다
- **「매칭 검수 대기」 처리 대기 배지** — 누를 곳이 없는 배지는 숫자만 있고 할 일이 없다
- **`ref_store_count` · `ref_onnuri_count`** (홈페이지 게시값을 따로 받던 칸) — 점포수는
  ⚙ 산출값 둘로 합쳐졌다. **2026-08-25 부터 그 둘을 손으로 고칠 수 있지만** 게시값을
  따로 들고 있는 칸이 돌아온 것은 아니다 — 산출값 자체를 덮어쓴다 (아래 「점포수를 고친다」)
- **권한 구분 자체** (`CITY` · `DEVELOPER`) — 이 화면을 쓰는 사람이 용인시 담당자뿐이라
  업무에 나눌 등급이 없다 (2026-08-20). 계정 항목표에서 `role` 이 빠졌다.
  2026-08-24 에 계정 관리 하나가 최종 관리자(`admin`)에게만 열렸지만 `role` 은 돌아오지
  않았다 — 판정을 아이디로 한다 (아래 「계정」)
- **QR 식별자 자동생성** — 화면이 지어낸 코드는 안내판에 인쇄된 코드와 맞을 이유가 없다
  (2026-08-20). 같은 줄에 있던 **[QR 지점 등록]은 2026-08-25 에 돌아왔고**(수정·삭제는
  2026-08-24), 등록 창에서도 코드는 담당자가 적는다 — 자동생성만 없는 채로 남는다
  (아래 「QR 지점을 전부 고치고 지운다」)
- **API 쿼터 설정 구획** — 한도·임계치는 카카오 계약과 서버가 정하는 값이라 화면에서 손댈
  자리가 아니다. 오늘 사용량은 대시보드가 그대로 보여준다
- **「조회수 상위 점포 10 · 조회수 상위 공공시설 10」 순위표** — 시민 화면에 그런 목록이
  없다 (2026-08-20). 그 자리는 상점가를 골라 **둘러보기 탭의 두 레일을 그대로 보는**
  구획이 대신한다. 담당자가 보는 여섯 곳이 곧 시민이 보는 여섯 곳이다

지운 파일: `pages/MatchQueue.jsx` · `pages/Sync.jsx` · `pages/BulkUpload.jsx` ·
`data/queue.js` · `data/bulkUpload.js` · `data/zones.js` · `data/districtRef.js`.
관리자 번들이 **120모듈 1,022KB → 113모듈 935KB** 로 줄었다.

## 입력 항목은 명세서가 정한다

`data/fields.js` 가 **명세서의 항목표를 그대로 들고 있고**, 폼 열이 전부 거기서 나온다.
화면이 항목을 하나 더 넣고 싶어도 넣을 자리가 없다 — 그게 이 구조의 요점이다.

폼이 지키는 것 여섯:

1. **명세서에 있는 항목만.** 없는 칸을 만들어 두면 담당자는 채워야 하는 것으로 읽고,
   채운 값의 출처는 아무도 모른다
2. **필수 열 네 값이 화면에서 서로 다르게 보인다.** ● 필수 · ○ 선택 · ◐ 조건부 · ⚙ 자동을
   각각 다른 배지로 적는다. 하나로 뭉개면 담당자가 ⚙ 칸을 비어 있는 필수 칸으로 읽고
   아무 값이나 채운다 — 그 순간 집계값이 수기값이 된다.
   **⚙ 는 곧 읽기 전용이다** (2026-08-25) — ⚙ 이면서 고칠 수 있던 칸 셋(점포수 둘 ·
   업종 칩)이 ● 이 되면서 그 예외가 없어졌다. 자동으로 채워지되 담당자가 정하는 값은
   ● 이고, 자동으로 채워진다는 사실은 배지가 아니라 칸 밑 한 줄이 적는다
3. **범위를 칸 아래에 그대로 적는다.** `2~40자` · `0~9999`. maxlength 로 막기만 하면
   담당자는 글자가 더 안 써지는 이유를 모른 채 지운다
4. **선택 항목을 비우면 시민 화면에 `-` 가 뜬다**고 폼 아래 한 줄로 적는다
5. **가부 항목은 Switch, 저장값은 불리언.** 표시(○ · ×)는 읽는 쪽이 정한다
6. **데이터 기준일 칸이 없다.** 카테고리 단위로 M14 에서 정한다 (명세서 7장)

### 이름이 둘인 이유

명세서는 `address_road` · `store_count` 처럼 **DB 컬럼명**으로 항목을 부른다. 그런데
시민용 화면 열둘이 이미 `addr` · `stores` 를 읽고 있어, 이름을 바꾸면 잘 돌고 있는 화면
열둘을 뜯게 된다. 그래서 **키는 우리 것을 쓰고 명세서 이름을 `spec` 에 적어 둔다.**
서버 연동 때 이 한 표가 곧 매핑표가 된다.

## 데이터

읽기 원본은 **시민용과 같은 파일**이다. 복사본을 만들면 둘이 갈라져, 관리자에서 고친 값이
시민 화면에 없는 상태가 곧바로 만들어진다.

```
읽기  screens/main/data/{facilities,dunjeon,districts,qr}.js
      admin/data/sources.js                  ← 위 표에 빠진 기본값을 채운 것
쓰기  admin/data/store.js                    ← 원본 위에 덮개(overlay)
관리자 전용  admin/data/{fields,account,stats,reports,settings,assets}.js
```

**화면은 `sources.js` 를 읽는다** (2026-08-25). 시민 화면의 표는 시민 화면이 쓰는 값만
갖고 있어서, 「노출 여부」가 아무 줄에도 없고 점포의 「소속 골목형 상점가」도 없다. 전에는
목록 화면들이 그 빈자리를 **읽는 자리마다** 메웠다(`visible !== false` · `districtId || 둔전`).
목록은 그래서 맞게 보였는데 **폼은 아니었다** — 폼은 값을 그대로 읽으므로 스위치가 전부
꺼진 채로 서고, 필수인 소속 상점가가 빈 칸이라 손대지도 않은 항목이 저장을 막았다.
메우는 자리를 한 곳으로 옮겨 목록과 폼이 같은 줄을 읽는다. 원천 배열은 손대지 않는다 —
시민 화면이 그것을 읽고 있다.

`store.js` 의 덮개가 갖는 것은 다섯이다 — `edits`(바뀐 필드만) · `added`(통째 행) ·
`removed`(id) · `links`(연쇄 삭제로 함께 지운 id) · `history`(변경 이력). 읽을 때 원본에 겹쳐 목록을 만든다. 실연동 때는 이
파일이 통째로 fetch/POST 로 바뀌고 화면 코드는 `useCollection` 의 모양만 같으면 손대지 않는다.

> **여기서 고친 것은 시민용 화면에 반영되지 않는다.** 서버가 없어 둘이 자료를 주고받을 길이
> 없고, 덮개는 `sessionStorage` 에 있는데 그 저장소는 **탭 단위**라 시민용 화면을 다른 탭에서
> 열면 애초에 닿지 않는다. 화면 상단의 노란 띠가 이 사실을 늘 적어 둔다.

상단바에 있던 **[데모 데이터 초기화]** 는 뺐다 (2026-08-20). 모든 화면 맨 위, 늘 보이는
자리에 **고친 것을 통째로 되돌리는 버튼**이 서 있을 이유가 없다. 처음 상태로 돌리려면 탭을
닫았다 열면 된다 — 덮개가 `sessionStorage` 라 그것으로 끝난다. 되돌리는 함수 자체는
`store.js` 의 `resetAll` 로 남아 있어 필요하면 다시 어디든 붙일 수 있다.

### 삭제는 영구다 (2026-08-24, 사용자 요청)

같은 날 앞선 판에서 **「전체 | 삭제된 항목 n」 탭**을 목록 화면 다섯(상점가 · 점포 · 축제 ·
공공시설 · 계정)에 세웠다가 **통째로 걷어냈다.** `pages/RemovedItems.jsx` 도 함께 지웠다.
지금 [삭제]는 확인 창에서 한 번 더 확인하면 그것으로 끝이고, 되돌리는 자리는 화면에 없다.

- **확인 창의 첫 문장이 그 사실이다** — 「삭제한 항목은 복구할 수 없습니다.」 마지막 줄이
  아니라 **맨 앞**인 것이 요점이다: 담당자는 이미 [삭제]를 누르고 들어왔고 상자를 끝까지
  읽지 않을 수도 있다. 순서는 **되돌릴 수 없다 → 더 나은 길**(폐업·폐쇄라면 [노출 여부]를
  끈다)이고, 그것이 "멈춰야 하나"를 판단하는 순서다 (`DELETE_NOTE`). 자기 문장을 쓰는
  화면 셋(축제 · QR 지점 · 계정)도 첫 줄은 같다.
  **두 문장이 된 것은 2026-08-25 다** (사용자 요청) — 가운데 있던 「사용자 화면과 현재
  목록에서 즉시 사라집니다」는 [삭제]를 누른 사람이 이미 아는 일이다
- **덮개에는 `removed` 배열이 남아 있다.** 원본 배열(`STORES` · `FACILITIES`)이 모듈 상수라
  거기서 행을 뺄 수가 없어서, 원본에서 온 행은 id 를 적어 두고 `merge` 에서 거른다.
  종전과 다른 점은 그 목록이 **비석이지 서랍이 아니라는 것**이다 — 읽는 화면도 되돌리는
  함수도 없다. 실연동에서 이 자리는 서버의 DELETE 다
- **새로 등록한 행은 진짜로 없어진다** — `added` 에서 빼내고 남은 `edits` 도 함께 지운다
- **저장 키를 `v2` → `v3` 으로 올렸다.** v2 덮개에는 되돌리기용으로 `added` 에 남겨 둔 채
  `removed` 에도 오른 행과 연쇄 삭제 기억(`links`)이 들어 있어서, 그 모양을 새 코드가
  읽으면 지운 줄이 목록에 되살아난다
- **잃는 것**: 잘못 지운 한 건을 되찾는 길이 없다. 남는 것은 변경 이력의 「삭제」 한 줄
  (무엇이 없어졌는지는 알 수 있으나 되살리지는 못한다)과 상단바의
  **[데모 데이터 초기화]**(그날 고친 것을 **전부** 버린다)뿐이다. 그래서 **지우기 전에
  보여주는 것**이 유일한 안전장치가 되고, 아래 상점가 연쇄 삭제의 목록이 그만큼 무거워진다

### 상점가는 연결된 것과 함께 간다 (2026-08-24)

명세서 10장의 "진행 중 축제 또는 활성 QR이 연결된 상점가는 삭제를 차단한다"를 **뒤집었다.**
막다른 길이었기 때문이다 — 상점가 하나를 정리하려면 축제 화면에서 축제를 지우고, QR
화면에서 지점을 지우고, 다시 돌아와야 했다. 세 화면을 오가는 동안 무엇을 지웠는지 스스로
기억해야 하고, 중간에 그만두면 **축제만 없어진 상태**가 남는다.

이제 **축제 · QR 지점 · 소속 점포가 함께 지워진다.** 확인 창이 함께 갈 것을 먼저 보여준다.
한 번의 결정이 되므로 막을 이유가 없다.

**되돌리기는 없어졌다** (2026-08-24, 위 절). 이 길을 열 때의 근거 절반이 "그 결정을 통째로
되돌릴 수 있다"였는데 그 절반이 사라졌으므로, 남은 안전장치는 **지우기 전에 보여주는
목록 하나**다. 그래서 이 화면의 확인 창은 다른 화면보다 할 일이 많다.

- **점포도 함께 간다** (2026-08-24 같은 날 고침). 처음에는 점포만 빼 두었는데
  ("335곳을 한 번에 지우는 일은 이 화면이 할 일이 아니다"), **그러면 남은 점포를 볼 수
  있는 자리가 없다.** 시민 화면에서 점포에 닿는 길은 상점가 탭 하나뿐이고, 관리자 점포
  목록에서는 없어진 상점가 이름이 필터에 남는다. 어디에도 뜨지 않는 자료를 "남겼다"고
  말하는 것은 기록으로도 틀리다 — 그것은 남은 것이 아니라 찾을 수 없게 된 것이다
- **확인 창이 셋을 다르게 적는다.** 축제와 QR 지점은 **이름으로**(「축제 · 둔전 골목축제」
  「QR 지점 · 둔전 시장 입구」), 점포는 **곳수로**(「점포 · 335곳」). 335개 상호를 늘어놓으면
  확인 창이 아니라 목록이 되고, 여기서 알아야 하는 것도 어느 가게인지가 아니라
  **이만큼이 함께 간다**는 크기다
- **QR 지점의 빠져나갈 길은 여기 적지 않는다** (2026-08-25, 사용자 요청). 2026-08-24 까지는
  QR 이 걸렸을 때 한 줄이 더 섰다 — 「안내판은 현장에 그대로 남습니다. 지점을 지우지
  않으려면 [QR 지점 관리]에서 소속 골목형 상점가를 먼저 옮겨 주세요.」 이 창이 하는 일은
  **함께 지워지는 것을 보여주는 것**이고, 위 목록이 QR 지점을 이름으로 이미 적는다.
  옮기는 절차까지 적으면 지울지 말지를 정하는 자리에서 다른 화면의 사용법을 읽게 된다 —
  안내판이 현장에 남는다는 사실은 **QR 지점 관리의 삭제 확인 창**이 그 일을 하는 자리에서
  적는다 (`DELETE_NOTE_QR`). 길 자체는 그대로 있다: 소속을 옮기거나 [지정 안 함]으로 두면
  그 지점은 남는다
- 컬렉션을 넘나드는 삭제라 `store.js` 의 `removeRows`(훅 밖 함수)를 쓴다.
  상점가 화면이 축제·QR·점포 컬렉션을 통째로 세울 이유가 없고, **여럿을 한 번에 넘기는
  것이 중요하다** — 점포 335건을 한 건씩 지우면 저장이 335번 돌고 변경 이력이 그것만으로
  가득 찬다 (`HISTORY_MAX` 200). 이력에는 「일괄 삭제 · 점포 · 둔전 골목형상점가 삭제」
  한 줄로 적는다
- **QR 지점에는 빠져나갈 길이 있다.** 축제는 상점가와 함께 없어지는 것이 맞지만 안내판은
  현장에 그대로 붙어 있다. 지우기 전에 [QR 지점 관리]에서 소속 상점가를 옮기거나
  [지정 안 함]으로 두면 지점이 남는다 (아래 「QR 지점의 소속 상점가」). 확인 창과 그 화면의
  안내 줄이 둘 다 이 방법을 적는다 — 그 화면에는 삭제 버튼이 없어서, 적지 않으면 어제
  있던 지점이 없어졌는데 화면 어디에도 이유가 없는 상태가 된다

### 점포수를 고친다 (2026-08-25, 사용자 요청)

「점포수」와 「온누리 가맹 점포수」는 ⚙ 산출값이라 못 고치는 칸이었다. 근거는 *"관리자가
32개소 숫자를 옮겨 적을 필요가 없다"* 였는데, **잠글 이유는 아니었다** — 점포 자료가 있는
상점가가 32곳 중 한 곳(둔전)뿐이라 나머지 31곳의 수는 애초에 세어 나온 값이 아니고, 현장에
한두 곳이 새로 들어왔는데 점포 자료 갱신이 아직이면 그 사이 내내 사용자 화면 머리글이 틀린
수를 적는다.

업종 칩(`chipManual`)과 같은 처리다. **배지는 처음에 ⚙ 로 두고 칸만 열었다가
(`editable`), 같은 날 ● 으로 바꿨다** (사용자 요청) — ⚙ 인 채로 열려 있는 칸은 「사람이
넣지 않는 값」과 「여기 넣으세요」를 한 자리에서 함께 말한다. 그 예외를 쓰던 항목이 셋
(점포수 둘 · 업종 칩) 다 ● 이 되면서 `editable` 자체가 없어졌다.

- **손으로 고치면 그 뒤로 집계가 덮지 않는다** (`countManual`). 이 갈래가 없으면 칸만
  열어 놓아도 둔전에서는 아무 일도 일어나지 않는다 — 세는 쪽이 매 렌더 다시 이겨서
  담당자가 보기에는 저장이 안 된 화면이 된다
- 수정 창을 열면 **센 값이 칸에 들어와 있다.** ● 이 되었다고 담당자가 하는 일이 늘지
  않는다 — 그대로 저장하면 계속 세는 값을 따라간다
- 고친 줄에는 목록에 **「수기」 배지**가 붙는다. 없으면 점포 목록 건수와 이 수가 어긋났을 때
  어느 쪽이 고장인지 알 수 없다
- **되돌리는 자리는 없다 — 센 값과 같게 적으면 자동으로 돌아간다.** 같은 이유로, 열어보기만
  하고 저장한 경우는 수기로 치지 않는다
- 온누리 가맹 수가 점포수를 넘으면 저장이 막힌다 (`extraValidate`)

### QR 지점을 전부 고치고 지운다 (2026-08-24, 사용자 요청)

M12 는 오래 **현황만** 갱신했다 — 고칠 수 있는 것이 소속 상점가 · 설치 상태 · 설치일자 ·
활성 여부 · 설치 상세 위치 · 관리 메모 여섯뿐이었고, 지점을 가리키는 넷(식별자 · 지점명 ·
주소 · 좌표)은 창 위쪽에 읽기 전용으로 적기만 했다. 삭제 버튼도 없었다. 근거는
**안내판에 인쇄되어 현장에 붙은 값**이라는 것이었다.

**그 사실은 지금도 맞지만 잠그는 방식이 아니게 됐다.** 인쇄물이 잘못 나갔거나 지점명이
실제와 다르거나 좌표가 100m 틀린 경우에 담당자에게 남는 길이 없었다 — 그 좌표 하나에
시민이 보는 모든 거리가 매달려 있는데도. 이제 화면은 **무슨 일이 일어나는지를 적고
결정은 담당자가 한다**:

- 식별자 칸에는 **안내 줄을 두지 않는다** (2026-08-25, 사용자 요청. 하루 전까지는
  「안내판에 인쇄된 코드입니다. 바꾸면 …」을 적었다) — 코드를 고치는 일은 드문데 그 줄은
  모든 열람에 서 있었다. 무슨 일이 일어나는지는 그 일을 하는 자리에서 말한다
- **식별자는 전역 유일**이라 저장 전에 겹치는지 검사한다 (`extraValidate`) — 겹치면 시민이
  그 코드를 찍었을 때 어느 지점으로 갈지가 표의 차례로 정해진다
- 주소를 바꾸면 좌표가 따라온다 (점포·공공시설과 같은 `onAddress` 한 줄)
- 표에 [삭제] 열이 생기고, 확인 창의 각주가 **이 화면만의 대안**을 적는다 (두 문장.
  2026-08-25, 사용자 요청): 「삭제한 항목은 복구할 수 없습니다. QR 코드를 교체했다면
  삭제 대신 설치 상태를 [철거]로 두고 [활성 여부]를 비활성으로 돌려주세요.」
  가운데 있던 「안내판은 현장에 그대로 남아 있어 …」는 **왜 안 되는지를 설명하는 문장**
  이라 뺐다 — [삭제]를 누르고 들어온 사람은 이 상자를 끝까지 읽지 않을 수 있다.
  **「지우지 말고 끄라」는 원칙은 그대로이고, 지키게 하는 방법만 바뀌었다** —
  버튼을 없애는 것에서 결정하는 자리에서 말하는 것으로

**[QR 지점 등록]도 열었다** (2026-08-25, 사용자 요청). 하루 전까지는 「붙어 있는 지점을 고치는
것과 없던 코드를 지어내는 것은 다른 일」이라며 남겨 두었던 자리다. 그 말은 맞지만 결론이
틀렸다 — **안내판이 현장에 서고 나면 그 코드는 어딘가에 반드시 등록되어야 한다.** 화면에
자리가 없으면 그 일은 없어지지 않고 개발 쪽 요청으로 넘어가며, 담당자는 안내판을 붙여 놓고
기다린다. 푸는 방식은 위와 같다:

- **등록 창에 따로 안내를 세우지 않는다.** 여는 순간 넉 줄짜리 안내 상자(「안내판은 이
  화면에서 만들어지지 않습니다 …」)와 식별자 칸의 등록 전용 안내 줄(`NEW_CODE_HINT`)을
  세웠다가 **같은 날 걷어냈다** (사용자 요청). 거기 적힌 것이 전부 화면에 이미 서 있다 —
  식별자 칸은 「안내판에 인쇄된 코드입니다」를 항목표에서 그대로 받고, 기본값은 창이
  열릴 때 설치 상태 고르개와 꺼진 스위치가 보여주며, 설치를 마치고도 켜지 않은 채 두면
  수정 창의 경고 상자가 그 사실과 할 일을 적는다
- **자동생성은 그대로 두지 않는다.** 등록 창에서도 코드는 담당자가 적는다
- **소속 없음 안내 상자는 등록 창에 서지 않는다** — 아직 아무것도 고르지 않은 것이 당연하다
- 덮개의 열쇠가 여기서만 갈린다: 원본 표의 행은 `id === code` 지만 화면에서 등록한 행의
  id 는 덮개가 매기는 `qr-new-001` 이다. 화면과 시민 화면이 보는 값은 언제나 `code` 다

**소속 상점가는 2026-08-24 앞선 판에 먼저 나와 있었다.** 어디에도 인쇄되지 않는 값이고,
위의 연쇄 삭제 때문에 바뀌어야 하는 자리가 먼저 생겼기 때문이다. 고르개에는 **지금 살아
있는 상점가만** 오른다 (`readCollection("districts", …)`) — 지워진 상점가가 남아 있으면
지점을 옮겨 살려 두려던 담당자가 방금 지운 상점가를 다시 고르게 되고, 그 지점은 그대로
다시 사라진다.

### M12 수정 창의 설명 세 줄을 정리했다 (2026-08-24)

| 어디 | 무엇 |
| --- | --- |
| 읽기 전용 목록 아래 | *"위 네 값은 안내판에 인쇄되어 … 아래 항목만 고칠 수 있습니다"* — **삭제** (그 목록 자체도 곧 없어졌다. 위 절) |
| 활성 여부 | *"끄면 이 코드로 들어온 사용자에게 교체 안내가 뜹니다. 기본값은 꺼짐입니다"* — **삭제** |
| 설치일자 | *"설치완료를 고르면 필수가 됩니다"* → **"설치완료를 선택하면 필수 항목으로 설정됩니다"** |

**첫 줄은 화면이 이미 하고 있는 말이다.** 위 넷은 입력칸이 아니라 글자로 적혀 있고 아래는
입력칸이라, 어느 쪽을 고칠 수 있는지는 눌러 보기 전에 생김새로 갈린다. 고칠 수 없는
이유(인쇄물)는 담당자가 이 창에서 할 일을 바꾸지 않는다.

**둘째 줄은 틀린 말이 됐다.** 시민 화면이 훼손·철거(S11)와 준비 중(S11-A)을 가르면서,
꺼져 있을 때 뜨는 것이 **설치 상태에 따라 갈린다** — 설치완료인데 꺼져 있으면 「교체 안내」가
아니라 「아직 준비 중」이다. 그 조합은 이 창의 경고 상자가 맡는다 (`QrPoints.jsx`).
그 상자는 **사용자 화면 문구를 인용하지 않는다** (2026-08-25, 사용자 요청) — 「설치는
완료되었으나 현재 비활성 상태입니다. 운영을 시작하려면 [활성]을 켜 주세요.」 두 문장이다.
인용은 저쪽이 바뀔 때마다 여기도 고쳐야 하는 줄이었고(S11-A 가 생기면서 실제로 한 번
고쳤다), 담당자가 지금 할 일과는 상관이 없다 — 켜면 그 안내는 사라진다.
뒷 문장(기본값)은 새로 만드는 자리의 이야기인데, **이 화면은 지점을 만들지 않는다.**

셋째 줄에서 「설치완료」를 붙여 쓰는 것은 그것이 **바로 위 칸에서 고르는 선택지의 이름**이기
때문이다. 띄어 적으면 목록에 없는 값을 가리키는 줄이 된다.

## 계정 (2026-08-24 개정)

| 계정 | 볼 수 있는 화면 |
| --- | --- |
| `admin` / `admin1234!` — 최종 관리자 | 10개 전부 (**계정 관리 포함**) |
| `yongin` / `yongin1234` — 담당자 | 9개 (계정 관리 없음) |

**업무 화면에는 등급이 없다.** `CITY`(시청 담당자)와 `DEVELOPER`(개발자)를 없앤 v1.1 은
그대로다 — 시설·점포·축제·QR·신고를 고치는 일에 등급을 매길 이유는 지금도 없고, 아홉
화면은 두 계정이 똑같이 쓴다.

**갈리는 자리는 계정 관리(M15) 하나뿐이고, 이유는 업무가 아니라 자물쇠다.** 모든 계정이
계정을 지울 수 있으면 서로를 지울 수 있고, 마지막 하나를 쓰던 사람이 인사이동으로 떠나면
**아무도 못 들어온다.** 「마지막 계정 보호」는 계정이 0이 되는 것만 막을 뿐 *누가* 남는지는
정하지 못한다. 그래서 **지워지지 않는 계정 하나**(`admin`)를 두고 계정 관리를 그 계정에만
연다 — 담당자가 바뀌어도 돌아올 자리가 늘 남는다.

[삭제] 버튼만 감추는 것이 아니라 **화면을 통째로** 가린다. 화면이 열려 있으면 남의
비밀번호를 바꿀 수 있고, 그러면 `admin` 을 못 지우게 막아 봐야 그 비밀번호를 바꿔
들어가면 그만이라 자물쇠가 아무 것도 잠그지 않는다. 담당자가 비밀번호를 바꾸는 통로는
로그인 화면의 **초기화 요청**이다 (명세서 9장) — 최종 관리자가 계정 관리에서 넣어 준다.

**그 요청이 도착하는 자리가 계정 관리의 두 번째 탭이다** (2026-08-24). 제목 아래 탭이
「전체 | **비밀번호 초기화 요청 n**」 이고, 좌측 메뉴의 [계정 관리]에도 대기 건수가
배지로 붙는다. (셋이었다 — 가운데 「삭제된 항목 n」이 같은 날 함께 빠졌다.) 그 전에는 로그인 화면의 [요청 보내기]가 "접수했습니다"를 띄우고
**아무 데도 남기지 않았다** — 명세서가 적은 흐름의 앞쪽 절반만 화면에 있었던 셈이다.

요청 줄을 누르면 그 계정의 수정 창이 열리고, **새 비밀번호를 넣어 저장하면 요청이 자동으로
[처리 완료]가 된다** (비밀번호가 실제로 바뀌었을 때만이다 — 이름 한 글자를 고치려고 연 창이
요청을 닫으면 안 된다). 요청은 지우지 않고 상태로 닫으며, 잘못 눌렀으면 [대기로] 되돌린다.
저장은 다른 컬렉션과 같은 덮개다 (`data/passwordResets.js` · `data/store.js`) — 탭을 닫으면
함께 비워진다.

판정은 `can()` 한 함수에 있고(`data/account.js`), 부르는 쪽(내비 필터·라우터)은 v1.1
때와 같다. 다른 계정으로 `#/accounts` 를 쳐서 들어오면 대시보드로 되돌아간다. 실서비스의
권한은 어차피 서버가 막는다. 계정 표와 비밀번호가 소스에 있는 것도 그래서다 — 감출
가치가 있는 비밀이 아니라 검수용 열쇠이고, 로그인 화면이 그 사실을 적는다.

동작 규칙: 로그인 5회 실패 시 10분 잠금 ·
**세션에 시간 제한 없음** (탭을 닫을 때까지 유지. 2026-08-24 — 8시간이었다) ·
**최종 관리자(`admin`)는 중지·삭제 불가** ([삭제] 자리를 비우고 토글을 잠근다) ·
**그 밖의 계정도 쓸 수 있는 계정이 하나만 남으면 중지·삭제 불가** (아무도 못 들어오게 된다) ·
지금 로그인한 계정은 스스로 삭제할 수 없다.

## 실행

```bash
npm run serve      # 로컬 서버 — 기본 8000
npm run build      # 번들 2개 생성 (시민용 + 관리자)
```

→ http://localhost:8000/admin/

로컬 개발에는 빌드가 필요 없다 (번들이 없으면 로더로 떨어진다). 시민용과 같은 규칙이다 —
`?dev=1` 을 붙이면 번들이 있어도 원본을 읽는다.

**카카오 SDK 도메인을 새로 등록할 필요는 없다.** 등록 대상은 경로가 아니라 출처(origin)라
`/screens/main/` 과 `/admin/` 이 같은 도메인이다. 주소 검색(V-02)과 좌표 지정(V-01)이 지도를 쓴다.

| 3건 누적 강조 | `#/reports` 목록에서 둔전시장 공중화장실 세 줄(`rp-012`~`rp-014`)이 붉게 서고 접수번호 옆에 「3건 누적」이 붙는다. **한 건을 처리완료로 옮기면 셋이 둘이 되어 강조가 세 줄에서 다 풀린다** — 미처리만 센다 |
| 일괄 처리 | 목록 다섯(점포 · 공공시설 · 골목형 상점가 · 축제 · QR 지점)에서 체크박스를 켜면 필터 줄 오른쪽에 단추가 선다 — 앞 넷은 [노출]·[숨김], QR 지점은 [활성]·[비활성]이다. **일괄 삭제는 없다** (삭제는 영구다) |
| QR 지점 등록 | `#/qr` → 제목 오른쪽 [QR 지점 등록] → 빈 폼이 뜬다. 설치 상태는 **설치예정**, 활성은 **꺼짐**에서 시작하고, 좌표 자리에 「도로명주소를 선택하면 좌표가 자동으로 입력되며 …」가 적혀 있다. 이미 있는 코드(`dunjeon-01`)를 적으면 저장이 막힌다. 저장하면 목록 끝에 새 줄이 생긴다 (탭을 닫으면 사라진다 — 서버가 없다) |
| QR 지점 수정·삭제 | `#/qr` → 줄을 열면 **열 항목 전부**가 입력칸이다. 식별자를 다른 줄과 같게 적으면 저장이 막히고, 주소를 다시 고르면 좌표가 따라온다. [삭제] → 확인 창 각주가 「안내판은 현장에 그대로 남아 있어 …」를 적는다 |
| 폼이 저장된 값을 그대로 보여준다 | 목록 넷(점포 · 공공시설 · 골목형 상점가 · 축제)에서 아무 줄이나 열면 **[노출 여부] 스위치가 켜져 있다** (목록의 토글과 같은 상태다). 점포는 [소속 골목형 상점가]에 「둔전골목형상점가」가, [등록 일자]에 날짜가 들어 있어 **아무것도 고치지 않고 [저장]을 눌러도 막히지 않는다** |
| 1:N 줄 삭제 확인 | `#/festivals` → 아무 축제나 → [프로그램 일정]의 휴지통 → **그 줄 아래에 「〈프로그램명〉 을(를) 지울까요? [취소] [삭제]」가 편다.** 지울 줄이 위에 그대로 보인다. 상자를 겹치지 않는 것은 ESC 가 폼까지 닫기 때문이다 (`Repeater` 머리말) |
| 이탈 확인 | 폼에서 무언가 고친 뒤 [취소] → "저장하지 않고 닫을까요?" |
| 연쇄 삭제 (10장) | `#/districts` → 둔전 삭제 → 확인 창이 함께 갈 축제·QR 지점을 이름으로, 점포를 곳수로 적는다. 확인하면 `#/festivals` · `#/qr` · `#/stores` 에서 그것들이 함께 사라진다 |
| 삭제는 영구다 (10장) | 확인 창 각주의 **첫 문장**이 「삭제한 항목은 복구할 수 없습니다.」 다. 확인한 뒤 어느 목록에도 되돌리는 자리가 없다 — 처음 상태로 가려면 상단바 [데모 데이터 초기화](전부 버린다)이거나 탭을 닫았다 여는 것뿐이다 |
| QR 빠져나갈 길 | 위 연쇄 삭제 창의 목록에 「QR 지점 · 둔전 시장 입구」가 있다. `#/qr` 에서 그 지점의 소속을 [지정 안 함]으로 바꾸고 오면 목록에서 QR 항목이 빠진다 — 그 지점은 상점가를 지워도 남는다 (안내 한 줄은 2026-08-25 에 뺐다) |
| 잠긴 값 고치기 | `#/asof` 와 `#/settings` 는 **읽기 → [수정] → [제출] → 변경 내용 확인** 세 걸음이다. 확인 창에 바뀐 줄만 「무엇이 무엇으로」로 뜨고, 취소하면 아무 일도 없다 |
| 변경 이력 (10장) | 무언가 고친 뒤 `#/settings` 맨 아래 |
| 상점가별 둘러보기 매장 | `#/dashboard` 아래쪽. 상점가를 고르면 그곳의 「인기 매장 6곳 · 신규 매장 6곳」이 나온다 — **시민 화면 둘러보기 탭과 같은 여섯 곳**이다. 둔전 말고는 점포 자료가 없어 안내만 뜬다. `#/stores` 에서 1위 점포의 노출을 끄고 오면 목록에서 빠진다 |
| 처리 대기 배지 | 대시보드 맨 위. **남은 배지는 「좌표 누락 점포」 하나이고, 자료가 온전하면 0건이라 이 줄이 통째로 안 보이는 것이 정상이다** — 명세서가 "0건이 아닐 때만 노출"이라고 정했다. 「미처리 오류신고」는 2026-08-20 에 뺐고(같은 숫자가 좌측 메뉴 [오류신고 관리] 옆에 늘 붙어 있다), **「설치 미완료 QR」은 2026-08-24 에 뺐다** — 설치예정과 「설치완료 + 활성 꺼짐」은 밀린 일이 아니라 정상 상태이고, S11-A 검수용 미활성 지점(`dunjeon-03`) 때문에 0 이 되지도 않아 「1」이 붙박이로 떠 있었다. 없어지지 않는 배지는 읽히지 않고, 그러면 좌표 누락이 진짜로 떴을 때 같이 묻힌다 |
| 세션 유지 | 무언가 고친 뒤 새로고침 → 남아 있다. 탭을 닫았다 열면 → 사라진다 |
| 좁은 화면 | 창을 1,024px 아래로 줄이면 안내 문구만 남는다 |
| 시민용 무영향 | `/screens/main/` 세 탭과 상세가 전과 같다 |
